# Editor automation

Coding agents, and any other local MCP client, can drive a running editor, and games, dedicated servers, and networked clients, through `HertaEditorMcp`: read their state and logs, capture windows, click and type in the editor's UI, and play with scripted input, without window focus or keystrokes.

## Running it

1. Start the editor with automation: `Herta --automation` (read-only) or `Herta --automation=write`. The log says where it listens.
2. Point the MCP client at `HertaEditorMcp`. The repository's `.mcp.json` registers the Windows Development build for Claude Code; on Linux use `Binaries/linux/x86_64/Development/HertaEditorMcp`. Build `HertaEditorMcp` before starting the client, since clients start their MCP servers when a session begins.

`HertaEditorMcp` finds the editor through `Saved/Automation/Session.json`, searching upward from its own folder for the repository, or under `HERTA_ROOT` when set. A session file left by an editor that crashed is harmless: the server keeps reading the file for up to 10 seconds until an editor answers.

## Games, servers, and clients

Development builds of `HertaGame` and `HertaServer` take `--automation` or `--automation=write` too, with `--automation-name=<name>`; Shipping builds refuse it. Names default to `game` for a game played alone, `host` for `--host`, `client` for `--connect`, and `server` for `HertaServer`, and are lowercase on disk. Each process registers its session under the user's settings directory (`Herta/Automation/<name>/Session.json`, `%LOCALAPPDATA%` on Windows and `$XDG_CONFIG_HOME` or `~/.config` on Linux), so a packaged game is found wherever it runs.

Every tool takes `target`: `editor` by default, or a name `automation_targets` lists with whether it answers. Games and servers offer `play_state` (also `network_state`), `play_input`, `play_teleport` (not on a networked client, whose player belongs to its server), `editor_capture` (not on a server), `audio_voices`, and `editor_log`. Their `play_state` adds `players`, every player's feet in player order, and a client's or server's replication statistics. An automated game keeps playing while unfocused and leaves the pointer alone, so several can run side by side; scripted input replaces the devices' only while a `play_input` run lasts. To test multiplayer, start `HertaServer --automation`, then two `HertaGame --connect=127.0.0.1:<port> --automation --automation-name=client-1` and `client-2`, drive each client with `play_input`, and compare the server's `players` with each client's.

## Tools

| Tool | Does |
|---|---|
| `automation_targets` | The editor and every game, server, and client with a session file, by the name `target` takes, with whether each answers now and allows writes. Answered by `HertaEditorMcp` itself. |
| `editor_status` | The open level, entity count, viewport size, whether writes are allowed, and Play state. |
| `editor_log` | Log lines after a cursor; pass the returned `since` and `generation` back to read only newer lines. |
| `level_entities` | Entities with IDs, names, components, and parent-relative translation, rotation, and scale, filtered by `name_contains`. |
| `viewport_capture` | Renders `frames_ahead` more frames, then returns what the viewport panel shows as a PNG read back from the GPU, scaled to at most `max_width`. The render target extends behind the editor's glass panels; the capture crops to the panel. |
| `editor_capture` | Returns the whole editor window from the next presented frame, with panels, menus, popups, and dialogs, as a PNG scaled to at most `max_width` (1600 by default). It copies the swapchain image before present and waits for the GPU once, so it costs nothing until asked. HDR10 frames are decoded from PQ with paper white as white. Use it to check UI; `viewport_capture` is cheaper for the scene. |
| `module_reload` | Reloads the open project's game modules, or the one `name` gives, from their current builds, keeping Play running with each system's state, and lists the systems. A build that cannot take the running state leaves the previous one running and says a restart is needed. Needs `--automation=write`. |
| `ui_items` | Items the editor laid out in its last frame, from ImGui's test-engine hooks: label without its `##id` part (or the text after `##` for widgets that draw their own label, such as menu items), window, screen rect, and whether each is disabled, checked, opened, or takes text. `contains` and `window` filter; `unlabeled` adds fields and other items without a label. Recording is on only in automation sessions; otherwise the hooks cost one branch per item. |
| `ui_click` | Clicks an item by `id`, or by `label` (exact before partial, optionally within `window`, the `index`-th of several), with the left, right, or middle `button`, or a `double` click, through ImGui's input queue rather than the operating system. Answers four frames later, once the click has landed. `x` and `y` instead click a screen position, for parts of a row that are not items. Needs `--automation=write`, since a click can save or delete. |
| `ui_scroll` | Turns the mouse wheel over the item `id` from `ui_items` by `lines`, positive down. Needs `--automation=write`. |
| `ui_drag` | Drags with the left button from the item `from` to the item `to`, both ids from `ui_items`, pressing, moving, and releasing over several frames as ImGui drag and drop needs, such as a Content Browser tile onto a folder. Needs `--automation=write`. |
| `ui_type` | Types `text` into the focused field, then presses `keys` in order: names such as `Enter`, `Escape`, `Tab`, `Up`, `F2`, a letter or digit, or chords such as `Ctrl+S`. Needs `--automation=write`. |
| `graph_open` | Opens a graph by content key, such as `Game/Logic/Shrine.hgameplaygraph`, in its document panel: Material Graphs, animation graphs, Audio Graphs, VFX Graphs, StateTrees, and gameplay graphs. |
| `graph_state` | Every open graph document: kind, key, unsaved edits, node and link counts, compile diagnostics with their nodes, and the nodes lit as running, such as Play's active StateTree states or gameplay graph nodes that ran in the last second. `graph` adds the draft as canonical graph text. |
| `audio_voices` | The editor's last 64 sound plays, newest first: asset, bus, voice, volume, pitch, seconds since it started, whether it still plays, and a spatial play's position, with the mixer's statistics. The engine keeps the record on the game thread from the commands it submits, so the real-time thread does no extra work. `playing` keeps only those still playing. |
| `ui_stats` | The last frame's UI over every native window: visible windows, draw lists, draw commands, vertices, and indices, the UI's GPU time, and the CPU time of the frame's phases. GPU timing of the UI turns on for the request and answers with the first result, within 30 frames. |
| `gpu_timings` | GPU milliseconds per render pass in the latest measured frame. |
| `viewport_view` | Brings a panel or document kind to the front with `focus`, such as `StateTree`; switches the `navigation` and `collision` overlays; points the editor camera from `position` at `target`; and returns the overlays, the camera, and the latest navigation build. |
| `play_start`, `play_stop` | Start Play, waiting up to 20 s for meshes and the character to load, or stop it. `at` [x, y, z] and `yaw` place the player there once Play runs. |
| `play_teleport` | Places the player's feet at `position` [x, y, z], facing `yaw` or keeping the current facing, standing and still, as a respawn does. The run and its clock carry on. |
| `play_state` | Player position, velocity, look yaw, grounded, crouched, sliding, mantling, and wall-running flags, the active movement mode, speed, wall contact and normal, ground normal, camera position and distance from the body, camera mode, animation state, and objective, each AI agent's StateTree state, feet, health, and whether it sees or remembers the player, and the loaded navigation's tiles, polygons, obstacles, and crowd agents. |
| `play_input` | Drives the player for a number of frames: `move` [strafe right, forward], `look` total [yaw left, pitch up] radians, `face` a world [x, z] point to turn toward on the first frame, `jump`, `throw`, `toggle_camera`, `ragdoll` (collapse or get up), and `attack` (swing the sword) on the first frame, `block` held, `sprint` and `crouch` held; `sprint` with `move` forward runs at 7.2 m/s, and without it at 4 m/s. `steer_to` [x, z] turns toward a point every frame and stops within 0.3 m of it; `until` stops early once `grounded`, `airborne`, `landed`, `mode_changed`, or `mode:<Name>` holds, naming a movement mode such as `WallRun`; `trace` N samples the mode, feet, velocity, ground, wall contact, animation state, and animation events every N frames and on every mode change. Returns the Play state with `framesPlayed`, `stoppedBy` (`frames`, `arrived`, or `until`), `animationEvents` counting each event the character fired over the run, and the trace. |
| `editor_commands` | The editor's console commands, their descriptions, whether each mutates, and whether this session may run those. |
| `editor_command` | Runs one console command line as the Output Log would and returns its exit code and message. Mutating commands fail with `read_only` unless the editor started with `--automation=write`. |

Scripted Play advances a fixed 1/60 s per frame, so the same input gives the same result however fast the editor is drawing. Play started by `play_start` belongs to the client until `play_stop`: the mouse, keyboard, and gamepads cannot move the player, and the world holds still between calls, so only `play_input` frames advance it and runs repeat exactly. Play started by hand stays interactive.

To test movement, place the player with `play_teleport`, run input with `until` and `trace`, and read the trace's mode changes instead of adding logging; for example, run at a wall `until` `mode:WallRun`, then jump `until` `landed` with `trace` 10.

## Design

- `Platform` owns the transport: named pipes on Windows that reject remote clients and only admit their owner, and Unix domain sockets with mode 0600 in the user's runtime directory on Linux. Messages are a 32-bit length and up to 16 MiB of UTF-8 JSON.
- `EditorCore`'s `FAutomationServer` runs one client at a time on its own thread. The first message must carry the random session token from the session file; tool calls queue for the editor's main thread, which answers at a safe point each frame, possibly frames later. Unanswered calls fail after 30 s, so a stalled editor never hangs the client. Every call is recorded in `Saved/Automation/Audit.log`.
- `EditorCore`'s `HandleMcpMessage` turns MCP JSON-RPC lines into replies, so the protocol is unit-tested without processes; `HertaEditorMcp` only reads stdin and forwards calls. Captures come back as MCP image content.
- Every console command declares whether it mutates: writes files, changes the open level, or changes other lasting state. `FEditorCommandRegistry::Execute` refuses those before they run when the caller may not mutate, so a read-only session gets `read_only` and nothing happens. Level edits are undo transactions in the editor's own history: `entity.move <id or name> <x> <y> <z>` moves an entity to a world position as one edit, and `level.undo` and `level.redo` take it back and forth. No tool runs a shell. UI clicks and typing go into ImGui's input queue, never the operating system's, and need a write session.

Added tools follow a real need, as these did; see Milestone 7.5 in [EngineDesign.md](EngineDesign.md).
