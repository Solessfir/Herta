# Animation

Status: Milestone 8 in progress. Skinned glTF models cook with their skeleton and clips, the runtime Animation module samples, blends, and skins them, and the player plays as an animated character in Play and the game with a first-person or third-person camera. Its state machine is authored as an animation graph on the canvas, and the Sandbox has an animation station. Milestone 8 is complete as of 2026-11-10, and Milestone 8.5 - Skeletal dismemberment is complete as of 2026-11-11.

## Modules

| Module | Kind | Owns |
|---|---|---|
| `Animation` | Runtime | `FAnimationLibrary` (an immutable skeleton and its clips, shared between characters) and `FAnimationPose` (one character's sampling and blending memory). ozz-animation's runtime jobs stay private to it. |
| `AssetPipeline` | Developer | Building ozz skeletons, clips, and root-motion tracks from glTF inside `HertaAssetWorker`, with ozz's offline builders and optimizer. |

ozz-animation 0.17.0 is a pinned submodule under `External/ozz-animation`, built as `OzzBase`, `OzzAnimation`, and `OzzAnimationOffline`. Only the Animation module and the asset pipeline include its headers. Cooked assets hold ozz archives as opaque bytes, so the Assets module and everything downstream never see ozz types.

## Cooked data

A skinned model (cooked format 3) carries:

- one skin influence per vertex: four joint indices and four unorm16 weights summing to one;
- a skeleton: joint names, parents in parent-before-child order, column-major inverse bind matrices, and the ozz skeleton archive;
- named clips: duration, the ozz animation archive, and an optional root-motion track.

Each archive is sealed with its size and XXH3 hash. ozz trusts its input and reads past the end of a truncated archive, so `FAnimationLibrary::Create` rejects a seal that does not match before ozz reads anything, then checks that the archive's joints match the cooked names and parents.

The root joint's horizontal travel is extracted at cook time, so clips play in place. A clip whose root moves less than 1 mm keeps no root-motion track. `FAnimationLibrary::GetRootMotion` returns the travel between two clip times, wrapping once through the end for looping clips.

## Runtime

`FAnimationPose::Evaluate` samples up to eight weighted layers, blends them, and computes joint model transforms and skinning matrices (model transform times inverse bind matrix). Each layer slot keeps its own ozz sampling context, because a context caches the keyframes of the last clip it sampled. With no layers, or no positive weight, the pose is the bind pose. Evaluation allocates only the first time a new layer slot is used.

`FAnimationStateMachine` runs compiled state machine data: float, bool, and trigger parameters; states that play one clip or a 1D blend along a float parameter; and transitions with a duration, conditions that must all hold, and an optional wait for a non-looping state to finish. Transitions are tested in authored order, whether they leave the active state or any state, so the first one that can fire wins and the order is the priority. A blend advances at the weighted duration of the clips it mixes, so their phases stay in step. Interrupting a fade restarts it from the current state, so an interrupted fade can pop; blending from a frozen pose waits until a clip needs it. States carry named events at a phase from 0 (their start) to 1 (their end). `GetEvents` lists those the active state reached during the last update, once per pass, even when one update covers several loops; a state fading out fires none, and a zero-length update, as while paused, fires none and leaves the state's start for the next. The Animation graph will compile to the same data.

## Animation graph

Animation graphs (`.hanimgraph`) author state machines on the graph canvas, in GraphCore's canonical text under the `animation` domain. The developer AnimationGraph module holds the schema and the compiler; the editor, the asset cooker, and `HertaEditorCmd animation.compile <graph>` run it, and the runtime only sees the compiled `FAnimationStateMachineDesc`, which now lives in Assets so cooked models can carry it.

- **State** nodes output their state. Properties: name, clips (`Clip`, or `Clip@Position, Clip@Position` for a 1D blend along the blend parameter), blend parameter, loop, speed, and events (`Name@Phase, ...`).
- **Transition** nodes take the state they leave in From, or leave From unlinked to leave any state, and the state they enter in To. Properties: priority, duration, at end, and conditions (`Parameter` for a true bool or a fired trigger, `!Parameter`, `Parameter > Value`, `Parameter < Value`, separated by commas, all of which must hold).
- The **Entry** node takes the state the machine starts in. **Parameter** nodes declare floats, bools, and triggers with their defaults.

States and parameters compile in node order and transitions by priority, then node order, which is the order the machine tests them in. The compiler reports unknown or mistyped parameters, conditions that cannot hold for their type, malformed clip and event lists, duplicate names, and a missing entry, each on its node. `MakeAnimationGraph` lays out a state machine built in code as a graph, with each state's outgoing transitions stacked beside it and any-state transitions in their own column.

A skinned model's metadata names its graph with `Setting.AnimationGraph`; see [Asset pipeline](AssetPipeline.md). The Sandbox Mannequin's `Mannequin.hanimgraph` was generated from the built-in locomotion, `MakeDefaultPlayerStateMachine`, which models without a graph still run. The session drives parameters by name: Speed, Grounded, Crouched, Sliding, WallRunning, Jump, WallJump, and Mantle; a graph without one simply never sees it.

In the editor, **Edit animation graph** under the player character in the viewport settings opens the character's graph as a document tab, creating it beside the model from the built-in locomotion when the metadata names none; passing a `.hanimgraph` on the command line opens it too. The tab shares the Material Graph's document panel: undo, save, details with hints for each property, and diagnostics. Saving recooks the character for the next Play. Play pauses while the tab is in front, and the tab outlines the state and transition the character was in, in Play green; automation's `play_input` keeps stepping a paused Play, so scripted runs update the highlight live. Viewing the graph beside a running Play needs a split workspace, which the editor does not have yet.

## Player character

A level's `playerCharacter` (schema 11) names the skinned model the player plays as. `FGameSession` builds an `FPlayerCharacter` from the cooked model: the library, a pose, the default locomotion machine (an idle, walk, jog, and sprint blend by ground speed, crouching, slide start, loop, and exit, jump start, wall jump, air, and landing states, a mantle, and a wall run that plays the sprint cycle while the session leans the body, because the clips have none). It reads the mover's active mode, so it follows whichever modes the character uses, and its own copy of the mesh. Mantles and wall jumps are triggers from any state, listed first so they win. The mantle clip's root rises the 1 m it was authored to climb; the session draws the body lower by the pose's root height, and the first-person camera reads the head the same way, because the capsule already carries the body up the real ledge height. Every frame the pose is evaluated and skinned on the CPU (`SkinVertices`) into the mesh's vertex update, which shares the soft-body path for bounds, shadows, and ray-tracing refits. In first person the character draws two skinned copies through `FMeshRenderView::Visibility`: the intact body is hidden from the camera but casts shadows and appears to ray-traced reflections and global illumination, and a copy with the neck and head collapsed draws for the camera only. The camera sits 0.24 m ahead of and 0.07 m above the animated head joint, eased over about 50 ms, so it follows the body's lean, crouch, and slide without looking out through the neck, and looking down shows the chest and legs. The body follows the view yaw. In third person (V or the gamepad's North button) the body turns towards its movement, and a camera boom behind the shoulders sweeps a 0.2 m sphere with `FPhysicsWorld::CastSphere`, snapping in when something is in the way and easing back out. The locomotion blend fires `Footstep` at the start and halfway through each cycle while the player moves faster than 0.5 m/s, and landing fires `Land`; `FGameSession::GetCharacterEvents` exposes them for sounds and effects, and the automation `play_input` result counts them. Z (or the automation `ragdoll` flag) collapses the player into a ragdoll: `FPlayerCharacter::BuildRagdoll` fits eleven capsules (pelvis, chest, head, upper and lower arms and legs, 80 kg together) between Unreal-style skeleton joints in the current pose, and each frame the joints they drive follow them through `FAnimationPose::OverrideJoints`, while joints between and below them, such as the clavicles and fingers, keep their animated pose relative to their parent. The mover waits where the player collapsed, and the third-person camera follows the pelvis. Pressing Z again stands the player up over the pelvis and blends the body from the ragdoll's last pose back to the animation over 0.4 s; a ragdoll that falls below the respawn height returns to the start. A skeleton without those joints logs that it has no ragdoll. A model that cannot animate logs a warning and leaves the capsule playable.

## Slicing and severing

`SliceSkinnedMesh` cuts a skinned mesh along a plane through its current pose, the cut a sword blade makes. Each vertex is classified by its posed position; triangles that cross the plane split, and their new vertices interpolate bind-space position, normal, tangent, and UV, and blend the two corners' skin weights, keeping the four heaviest renormalized, so both halves animate from the same skeleton. Cut points are shared by every triangle on an edge and welded by position across UV seams, so the outline traces into closed loops. Loops nest: one inside an odd number of others is a hole in the smallest, such as a cut through a hollow shape. Each outline is triangulated with earcut, vendored under `External/earcut`, and both halves are closed with caps in a wound material slot, facing out of their half, with planar UVs in meters and normals turned back into bind space through the blended skinning matrix. Tangents are re-orthonormalized, as cooked models require. `SplitSkinnedMesh` is the same split along any per-vertex sign, which severing uses. Slicing is deterministic for the same pose and plane. It runs where the hit is found rather than on a task worker: the Mannequin slices in about 0.5 to 0.8 ms and severs in about 0.45 ms for its 7,538 vertices, under the 2 ms budget, and tests prove each half watertight, wound consistently, and holding the original volume between them, for a seamed sphere, a torus whose flat cut is an annulus, a posed mesh, and the Mannequin at several angles through a pose.

`FPlayerCharacter` keeps what is left of its mesh after cuts. Each cut first skins the body in the pose it is made in. `Slice` keeps the half holding the pelvis, which keeps animating and is uploaded as the body's new mesh, and returns the other half in bind space. `Sever` cuts off the limb below a joint where its skin weights pass to the parent and moves the stump's remaining limb weights onto the parent, so it does not stretch while the missing limb's joints keep animating. The split happens at runtime rather than being precomputed at cook time as first planned: it costs well under a millisecond, the same as a blade cut, and needs no extra cooked data, so the cook-time path waits until crowds make that time matter. A skinned model's metadata names its severable joints with `Setting.SeverableJoints`, a comma-separated list of non-root joints that cooking checks against the skeleton; the Sandbox Mannequin names its neck, shoulders, elbows, hips, and knees, which is also the default for models that name none. A cut that would leave either half with fewer than 40 triangles or under 4 cm across does not happen, so slivers stay on their neighbour. Every cut is validated as a cooked model even headless.

Cut halves become `FCharacterPiece`s: their share of the skinned mesh, with a snapshot of the skeleton's pose when cut. A piece that carries two or more joints of the ragdoll profile, those weighing more than half on at least eight of its vertices, falls as a ragdoll of just those parts, fitted to the snapshot and joined where the profile joins them, with parts whose profile parent was cut away hanging from the first part kept; every update overrides its joints from the ragdoll and skins it again. A smaller piece falls as one convex hull of up to 128 of its vertices, carrying its model space rigidly. Pieces are cut again the same way, from their current pose, into two new pieces.

## Sword and training dummies

The player carries a sword built from boxes, held in a grip frame computed each frame from the right hand's wrist, middle, index, and little-finger roots, so it does not depend on how the rig orients its hand bone: the blade leaves the fist on the index side, and its edge leads along the fingers. The left mouse button or the gamepad's right shoulder attacks and the right mouse button or left shoulder blocks; the built-in machine and the Sandbox graph add Attack A and B with their recoveries, chained by pressing again during a recovery, a Dash attack when attacking faster than 5.5 m/s, an Air attack that brings the sword down overhead when attacking in the air and plays out past the landing, a Block, a Hit reaction, and Dead. Attack states fire `SwingStart` and `SwingEnd` events, and a swing cut short before its end stops cutting after 0.8 s; between them the session traces the blade from guard to tip each update, and when a body's vertices, 256 at most and evenly picked, lie on both sides of the plane the blade swept since the last update and one near that plane falls inside the swept quad, it slices that character or piece along the plane, once per swing.

A Character component (level schema 12) plays its entity's skinned Static Mesh as a character with its model's state machine; see [Levels](Levels.md). The session gives it a kinematic capsule, so the player and thrown balls bump into it. A ball that touches the capsule flinches it, and with an impulse at least its Sever Impulse severs the limb whose joint lies nearest the hit. Cut pieces fall pushed away from the cut, and each character keeps its Maximum Pieces newest. A cut can leave parts joined to the rest only through a bone it took, such as a hand on the body's side of the plane without its forearm; `SplitJoinedParts` finds them by joint, since the Mannequin is built from many separate shells, and each falls as its own piece. Cuts that would leave either side under 8 cm deep are refused. A character that loses its head or its chest dies: it sets Dead, what is left of it detaches and collapses as a ragdoll piece, and its capsule goes. One that loses a foot, by any cut through a leg from the thigh to the ankle, is downed: it falls as its own ragdoll, built from the joints it still carries, and lives on the ground, where its capsule is gone, a guard leaves the navigation and no longer walks or swings but still sees and remembers, and blades and balls still cut it; each cut rebuilds the ragdoll without what it lost, and losing the head or chest kills it. `FGameSession::IsCharacterDowned` reports it. Characters animate in the fixed physics step, so the pose a ball severs against, and so the joint it chooses, is the same on every run; a blade cut is deterministic for the pose and plane, so it replicates from the hit. `FGameSession::SliceWorld` cuts everything a plane passes through, characters and pieces, for scripted blade tests. Restarting restores every character whole.

Deferred: a first-person projectionarms and held items, with their own field of view and compressed depth so they never clip into walls, until the sword arrives in Milestone 8.5; GPU skinning, until character or vertex counts make CPU skinning measurable in a frame (the Mannequin evaluates in about 0.013 ms and skins its 7,538 vertices in about 0.16 ms on one core in Development, plus a 362 KB upload).

The Sandbox character is Quaternius's CC0 Mannequin from the Universal Animation Libraries 1 and 2, merged onto one 65-joint rig; see `Games/Sandbox/Content/Characters/Mannequin/Source.md` for the exact source and the clips kept.
